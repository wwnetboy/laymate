# 文章组件选用与布局规范

写作或排版文章前读取本规范。它负责判断“内容该用什么组件”，[文章组件契约](components.md)负责准确的 Markdown 写法，模板负责最终视觉样式。选择模板不会改变组件的含义，也不意味着必须使用某一组组件。

## 先判断内容，再选择组件

用户的明确要求、已有内容和所选模板优先。只要求排版时保留原文，不为填充组件补写结论、风险、操作、数据或问答；允许润色时再调整表述和结构。

将正文段落作为默认载体。对准备突出的一段内容，依次判断：

1. **读者要做什么？** 是了解、照着操作、比较选择，还是回顾一个过程？据此确定文章主线。
2. **这段内容起什么作用？** 是必要解释、操作、并列项、引文、技巧、风险、结果核对，还是独立资料？先确定语义，后选组件。
3. **特殊组件是否帮助阅读？** 是否更容易找到操作、辨认风险、看懂比较或复查结果？如果只是为了让页面多一种颜色，保留正文或普通列表。
4. **是否与附近内容重复？** 同一句结论不同时放入正文重点、金句和摘要；新增组件要承担独立任务。

可在内部用“内容片段 → 阅读作用 → 组件 → 放置位置”做简短规划。不要把组件名称、排版分析或本规范写进面向读者的文章。

## 内容与组件的对应规则

| 内容的实际作用 | 推荐组件 | 选用条件与位置 | 容易误用的情况 |
| --- | --- | --- | --- |
| 文章名称 | 文件开头的 `# 标题` | 独立标题栏；用户有标题时优先保留 | 正文又重复一个同样的大标题 |
| 一组完整内容的主题 | `##` 章节标题 | 随阅读任务划分，如准备、操作、核对；模板自动编号 | 每个短段都建章节；新写标题再手工加“01” |
| 同一章节内的分支 | `###` 小标题 | 分支确实需要单独查找；一般以二、三级为主要层级 | 为改变字号跳级，或把标题放进提示框 |
| 背景、解释、叙述、论证 | 正文段落 | 默认选择，承接上下文和必要细节 | 普通解释全部套 `card` 或 `note` |
| 开头点明读者问题与文章帮助 | `lead` 或普通短段 | 导语确有帮助时使用，放在正文起始处 | 已有清楚开篇又加一段同义导语；每节都重复引言 |
| 一句话中的关键操作或判断 | 加粗 | 在正文中局部突出关键词或短结论 | 整段加粗导致没有阅读重心 |
| 必须被迅速找到的短重点 | 高亮或下划线 | 选择一种主要强调方式；与邻近强调区分主次 | 同一短语同时加粗、高亮、下划线 |
| 语气、名称，或确实作废的表述 | 斜体、删除线 | 斜体保留原文语气；删除线仅用于明确的修订或失效内容 | 用斜体承载大段核心操作；为了装饰划掉有效内容 |
| 文件名、参数、短命令等字面值 | 行内代码 | 精确字符需要保留且长度适合嵌入句子 | 把普通按钮名或一句观点都写成代码 |
| 他人原话、材料摘录 | `>` 普通引用，或 `quote` | 需要署名时用 `quote 来源或作者`；保留已知来源 | 把自己的操作说明伪装成引文，补造作者或来源 |
| 一段值得突出阅读的原话 | `pullquote` | 短而完整、确有引用意义；装饰引号自动生成，来源参数同 `quote` | 用它包装自己的总结；手工再补一层装饰引号 |
| 本文最值得记住的一个结论 | `takeaway` | 一句独立、可理解或可执行的结论；用在关键论述后或结尾 | 将长段、多条清单装成金句；每节都重复全文结论 |
| 不影响主线的背景、范围、条件 | `note` | 读者可按需阅读，放在所解释的内容附近 | 读者必须先做的操作藏在补充说明里 |
| 可选的省时技巧、快捷方法 | `tip` | 先让读者看懂主要方法，再给可选技巧 | 把必做步骤写成“可选技巧” |
| 存在实际后果的注意事项 | `warning` | 指明触发条件、可能后果及规避办法，放在相关操作前或紧邻处 | “记得保存”之类普通建议全部标警告；编造风险 |
| 操作后的可观察完成标准 | `success` | 告诉读者看哪里、什么结果才算完成，放在操作之后 | 把“这个工具很好用”或未经核对的结果写成成功状态 |
| 多个要点的摘要或回顾 | `summary` | 长文入口或复杂内容结束处，用于快速复查；短文可省略 | 和导语、核心结论逐字重复；每个短章节再加摘要 |
| 无先后关系的并列信息 | 无序列表 | 条件、特点、材料、选择项；各项层级相当 | 使用步骤组件让读者误以为必须按顺序做 |
| 简短的顺序、排名或枚举 | 有序列表 | 有顺序，但每项无需展开操作细节 | 有序编号本身就足够，却再添加大型步骤卡 |
| 需要逐项照做的操作流程 | `steps` | 各步写清动作，必要时补充输入、位置或预期结果 | 用于观点列表、卖点、菜单选项或发生过的历史 |
| 发布前或完成后逐项核对 | 任务列表 | 每项应可明确判断；这是静态清单 | 用勾选符号表示用户尚未完成的事；冒充可交互表单 |
| 同维度比较多个对象 | Markdown 表格 | 列是统一比较维度，单元格是短内容；适合选择与区别 | 长段解释塞进宽表格；只有两段故事也强行制表 |
| 可独立阅读的案例、材料或小档案 | `card` | 有清楚标题与边界、内部内容属于一个独立单元 | 用通用卡片替代已有语义的风险、技巧、定义 |
| 理解后文必需的陌生概念 | `definition` | 首次需要时解释，尽量紧邻出现位置 | 熟悉词语也逐个定义；加入与操作无关的技术架构 |
| 已提供或可确认的关键数值／短事实 | `facts` | 突出值加简短说明，必要时标明来源、时间或条件 | 为凑数据卡编造提效比例；将多个对象的比较拆散 |
| 主线结束后仍可能有的具体疑问 | `faq` | 问题与回答一一对应，补足边界或分支 | 把整篇必读教程藏进 FAQ；重复正文已解决的问题 |
| 随时间发生的变化、过程或里程碑 | `timeline` | 阶段或日期组织事实，强调“发生了什么” | 把“接下来怎么做”写成历史时间线 |
| 解释操作位置、结果或场景 | 图片与图注，必要时 `image` | 靠近相关文字；图注指出要看什么或验证什么 | 无关插图打断关键流程；只用截图承载必做步骤 |
| 内容性质明显转变 | 分隔线 | 如正文转文末附注，或主线转独立附录 | 标题已完成分区，还在每个段落后重复加线 |
| 访问工具或说明信息出处 | 文字链接、`source` | 正文链接放在需要访问处；文末来源统一整理 | 来源只剩“点击这里”；把访问入口全部藏在文末 |
| 可复制的代码、命令、配置或输入文本 | fenced code，标注正确语言 | 需要保留换行与精确字符；代码窗口自动提供苹果样式和高亮 | 为非技术文章展示样式而添加代码；把普通说明全塞进终端 |

完整语法、容器参数及图片外观见组件契约；不要自创未注册的组件或用原始 HTML 替代组件。

## 容易混淆的选择

**正文重点、核心结论与摘要：** 正文加粗帮助读者找到一句中的关键部分；`takeaway` 提炼一个结论；`summary` 汇总多个要点。需要保留论证的长段仍用正文。短文章不一定需要另加总结组件。

**引用与金句：** `quote` 用于完整引用，`pullquote` 用于需要突出的一段原话，`takeaway` 用于博主自己的结论。引用必须忠于材料，署名未知就不填；不能为了展示双引号样式制造引文。

**补充、技巧、警告与核对：** “这个方法适用的范围”是 `note`；“更快的可选办法”是 `tip`；“误操作会造成什么后果”才是 `warning`；“出现什么结果算完成”是 `success`。如果用户必须先做某件事，它应进入正文或步骤。

**步骤、清单与时间线：** 需要按顺序执行选 `steps`；只是逐项确认选任务列表；描述已经发生的进展选 `timeline`。同一过程无需再用不同组件完整重复一次。

**表格、关键数据与信息卡：** 比较多个对象的同一组维度选表格；突出少量已知事实选 `facts`；一个可以独立阅读的案例选 `card`。复杂叙述保持正文，不把“有信息”都理解成“需要信息卡”。

## 文章类型与布局参考

下面是可选的阅读路径，不是固定大纲。删除无内容支撑的环节，用户已有合理结构时保留它。

| 阅读目的 | 可采用的阅读路径 | 主要组件与使用边界 |
| --- | --- | --- |
| 工具使用／问题解决 | 遇到什么问题 → 适用条件或准备 → 操作 → 结果核对 → 必要的补充疑问 | 正文为主；较详细操作用 `steps`；真实注意点提前提醒；`success` 承接结果核对；有剩余问题才用 `faq` |
| 观点／知识解释 | 提出问题或观点 → 展开理由与证据 → 边界或反例 → 得出结论 | 正文承载论证；必要概念用 `definition`；原话用引用；关键结论可用 `takeaway`；不硬加步骤 |
| 方案比较／选择指南 | 明确选择目标 → 比较维度 → 差异 → 各类读者如何选 | 短差异用表格；长解释放回正文；只有已提供事实才用 `facts`；结论说明适用条件，不替所有人作同一选择 |
| 案例／经历／随笔 | 交代情境 → 变化或关键节点 → 具体细节 → 体会或启发 | 用正文保持叙述连贯；有明确阶段才用 `timeline`；独立案例资料可用 `card`；配图与叙述位置对应 |

## 组合、强调与阅读节奏

- **标题按主题分层。** 一节围绕一个可识别任务或论点；小标题用于真正的分支。新写章节不手工加模板序号。原文含有步骤号或有意义的编号时，不把它当装饰随意删除。
- **段落保持可读。** 普通手机阅读可先以每段两到四句为参考；逻辑完整性优先，长引文、代码和连续叙述不强行切碎。只要求排版时不借此改写原句。
- **正文承担主线。** 每个特殊组件都应能说清独立用途。通常让解释性正文成为主要载体；不按“每节必须有一个框”分配组件。
- **留白由模板控制。** 使用段落、标题和组件本身的间距，不插入空白字符、连串空行、额外横线或无内容卡片撑布局。
- **避免卡片套卡片。** 容器里优先放正文、列表、图片或必要代码。渲染器允许嵌套，但通常无需把提示再放进信息卡；确需嵌套时让内外层分别承担清楚的任务。
- **检查相邻重组件。** 连续多个提示框、金句、数据卡时，先检查能否合并、降为正文，或用解释性过渡连接。步骤、FAQ 或时间线内部的连续条目是同一组件的完整结构，不因此强行插入过渡。
- **保留清楚的主次。** 同一句优先一种强调；连续几段都加粗或高亮时缩小范围。警告色用于实际注意事项，不承担一般卖点强调。
- **长内容回到正文。** 提示、金句和表格不承担整段教程；需要展开时用正文说明，再用短框标出关键补充。不要只为缩短卡片删除必要信息。
- **比较适应手机。** 表格通常先考虑两到三列；内容太宽时改为逐项说明或列表。代码保留必要上下文，示例输入、输出或提示词用 `text`；实际命令用对应语言。
- **文末保持有用。** 摘要、FAQ、来源、行动提示按实际需要选择；不将它们全部追加为固定套餐。引用出处仍应能够关联到相应内容。

## 图片与文字的关系

插图解释场景，截图定位操作，结果图帮助核对。先说清读者要看哪里，再将图片放在对应段落或步骤附近；关键动作也要有文字说明。图注补充观察点，不只重复“这是截图”。

尊重用户已选的整篇配图外观。未选择时保持原图默认，不根据模板自动改成圆角阴影或苹果窗口。用户需要建议时，插画、照片或结果展示通常适合圆角阴影；软件操作截图通常适合苹果窗口；已有完整外框或需要忠实展示的图通常适合原图。截图已有窗口栏时，先考虑避免再套一层窗口。

同类图片优先跟随整篇默认，只有明确的单张需求才用 `:::image` 覆盖；图注留在框外。圆角、阴影和窗口只是 HTML 外观，不修改原图，也不自动应用到公众号封面。

## 选用示例

以下是用于判断的示例内容，不是对某个工具的功能或实测结果的声明。

| 内容片段 | 合理处理 | 不合适的处理 |
| --- | --- | --- |
| “准备记录，选择整理功能，检查待办，再保存。” | 简短流程用有序列表；每步需要解释时用 `steps` | 作为四条 `facts`，或者四张独立 `card` |
| “保存后，打开文件核对姓名、日期和待办。” | 作为操作后的 `success` 或核对清单 | 用 `pullquote` 包装成引文 |
| “把常用要求存下来，下次替换记录即可。” | 作为可选提效办法用 `tip` | 没有实际风险却使用 `warning` |
| “覆盖原文件会丢失旧版本，确认备份后再继续。” | 原文确有此事实时，在覆盖操作前用 `warning` | 等读者执行完才放在文末 FAQ |
| “两种方案的价格、适用人数、导出格式不同。” | 使用已提供的信息按相同维度制表 | 擅自补价格，或把长篇推测放进数据卡 |
| “先说清需要得到什么，再选择对应功能。” | 博主自己的结论用正文加粗或 `takeaway` | 加上双引号和虚构署名作为 `quote` |

同一段内容从正文改为组件，应只增加清晰的层级，不改变事实与语气。例如，一段详细操作可整理为：

~~~markdown
## 整理并核对记录

先准备要处理的记录，再按下面的顺序操作。

:::steps
1. **准备记录**

   找到需要整理的原始内容。
2. **提交内容**

   选择对应功能，填写希望得到的结果。
3. **核对并保存**

   对照原始记录检查姓名、日期和待办事项，再保存。
:::

:::success 完成后看这里
打开已保存的文件，确认内容完整，关键细节与原始记录一致。
:::
~~~

这里无需再追加金句、摘要、数据卡或 FAQ。若原文只有一句短操作，有序列表或普通正文即可，不为套用示例扩写成教程。

## 生成前与发布前自检

在生成 Markdown 前检查选用是否合适；生成后再检查实际排版。至少确认：

- 主线清楚，必要解释与操作可以直接找到，没有藏进补充框或 FAQ。
- 每个特殊组件都有明确作用，语义与内容一致；没有重复包装同一句话。
- 原文与用户选择得到保留；没有为了组件补造引文、数据、风险、成功结论或来源。
- 标题层级、组件密度与局部强调有主次；连续卡片和嵌套有明确理由。
- 代码语言与内容一致；精确文本和换行没有被润色破坏。
- 图片与所在段落对应，图注有用，外观遵守整篇与单张设置；封面独立处理。
- 生成 HTML 时按 SKILL.md 的流程检查手机阅读和复制效果，区分本地检查与实际公众号发布验证。

`assets/demo-article.md` 是用于检查所有组件的**组件全览**，不是日常文章的大纲。日常文章只使用内容需要的组件，不照搬“每种组件出现一次”的结构。模板的风格特色由渲染器负责，agent 负责语义、顺序与轻重。
